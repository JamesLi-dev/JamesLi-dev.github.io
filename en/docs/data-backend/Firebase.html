Firebase

Firebase 把认证、数据库、对象存储、函数、消息推送、监控和托管放在同一个平台里。做产品早期版本时，前端可以先接需要的部分，后面再把业务逻辑和数据边界补完整。

“装上 SDK 就结束”是个常见误解。接入前最好先定下几件事：

  • 哪些能力放在客户端直接调 Firebase
  • 哪些能力必须放到服务端，用 Admin SDK 或 Cloud Functions 接管
  • Firestore / Storage 的规则怎么限制
  • 本地调试、测试环境、正式环境怎么隔离
  • 流量和计费怎么避免失控

常用模块​

Auth​

处理注册、登录、第三方登录、匿名登录、多因素认证。

Web 项目一般这样分工：

  • Web 端直接用 Firebase Auth 做邮箱密码登录、Google 登录等
  • 服务端只负责校验 ID Token，识别当前用户是谁
  • 业务权限不能只看“前端是否登录”，还要由数据库规则或服务端接口执行

Firestore​

Firestore 是文档型 NoSQL 数据库，前端接入直接，也支持实时监听。

更适合：

  • 聊天、协作、轻后台、内容型产品
  • 需要前端直接订阅数据变化的页面
  • 前期需求变化比较频繁的项目

不太适合：

  • 复杂多表关联很重的业务
  • 强事务、复杂报表、跨维度统计很多的系统
  • 团队已经非常依赖传统 SQL 建模和查询能力的项目

Storage​

适合上传头像、图片、附件、音视频等对象文件。它通常和 Auth、Security Rules 一起用。

Cloud Functions​

适合放不能暴露给客户端的逻辑，比如：

  • 调第三方密钥
  • 支付回调处理
  • 发送邮件、短信
  • 数据同步和定时任务
  • Firestore / Storage 事件触发后的后处理

Analytics：记录用户做了什么​

Firebase Analytics 基于 Google Analytics 4，用来记录页面访问、产品行为和转化事件。它回答“用户做了什么”，不负责解释“页面为什么变慢”。

可以记录：

  • 页面浏览、搜索、筛选、播放、收藏等产品行为
  • 注册、登录、订阅、支付完成等转化事件
  • 业务维度，例如内容类型、套餐、来源渠道

不要把邮箱、手机号、姓名、完整 URL 查询参数或身份证号放进事件参数。参数应该服务于统计，用户资料应存放在业务数据库中。

Web 初始化​

import { getAnalytics, isSupported } from 'firebase/analytics'
import { app } from '@/lib/firebase/client'

export async function initAnalytics() {
  if (await isSupported()) {
    return getAnalytics(app)
  }
  return null
}

Analytics 只能在浏览器环境中初始化。SSR、Node 和不支持 Analytics 的浏览器需要跳过 getAnalytics()；同时，是否初始化还要服从项目的隐私同意策略。

记录事件​

import { logEvent } from 'firebase/analytics'
import { analytics } from '@/lib/firebase/analytics'

export function trackSearch(keyword: string, resultCount: number) {
  if (!analytics) return

  logEvent(analytics, 'search', {
    search_term: keyword,
    result_count: resultCount,
  })
}

最好维护一份事件字典，写清事件名、参数、类型和触发时机。页面组件不要自己拼事件名，否则报表里很快会出现 search、search_result、do_search 这种重复事件。

Analytics 排查​

  • 本地调试时事件不会立即出现在正式报表，可使用 DebugView 验证
  • 事件名和参数名要遵循 Analytics 规则，避免运行时被丢弃
  • 只在浏览器端初始化，避免 SSR 构建或服务端运行时报错
  • 生产环境应结合隐私同意、地区合规和数据保留策略配置采集范围
  • 如果需要把登录用户和行为关联，使用稳定的内部用户标识，并确认该标识不直接包含个人信息

官方 Web Analytics 初始化文档：Get started with Google Analytics for Web

Performance Monitoring：观察页面和请求​

Performance Monitoring 记录页面加载和 HTTP/S 请求的耗时，也可以用自定义 Trace 测量某个业务流程。它和错误监控、APM、日志系统是不同层次的工具。

Web 初始化​

import { getPerformance, isSupported } from 'firebase/performance'
import { app } from '@/lib/firebase/client'

export async function initPerformance() {
  if (await isSupported()) {
    return getPerformance(app)
  }
  return null
}

Firebase Web App 配置中必须包含 appId。Firebase 官方文档目前仍把 Web JavaScript SDK 标为 beta，接入后应先在测试环境观察兼容性，不要把它当成唯一的性能数据来源。Get started with Performance Monitoring for web

SDK 会自动收集页面加载和网络请求指标。数据按批次上报，首次接入后要打开页面并等待一段时间，控制台才会出现结果。

自定义 Trace​

import { trace } from 'firebase/performance'
import { performance } from '@/lib/firebase/performance'

export async function loadRecommendations() {
  if (!performance) return fetch('/api/recommendations')

  const recommendationTrace = trace(performance, 'load_recommendations')
  recommendationTrace.start()

  try {
    const response = await fetch('/api/recommendations')
    recommendationTrace.putMetric('result_count',
      Number(response.headers.get('x-result-count') ?? 0))
    return response
  } finally {
    recommendationTrace.stop()
  }
}

自定义 Trace 的名称应稳定、可聚合；用户 ID、搜索词、完整 URL 等高基数或敏感值不要作为自定义属性随意上报。需要区分用户群体时，使用有限枚举值，例如 plan: free | pro、region: cn | us。

它能做什么，不能做什么​

  • 它适合定位页面加载、请求耗时和特定流程性能，不负责捕获异常堆栈
  • 它不会替代前端错误监控、后端日志和分布式 Trace
  • 生产环境通常需要关闭开发环境采集，避免测试数据污染正式报表
  • 监控 SDK 自身也会增加少量初始化和上报开销，应关注 bundle 和网络请求
  • 如果项目已有 Web Vitals、Sentry 或 OpenTelemetry，先明确各工具的职责，不要重复采集同一指标

Cloud Messaging（FCM）：把通知送到浏览器​

Cloud Messaging 用来向浏览器推送通知。它只负责投递，不负责业务消息的存储、重试和分群。生产系统应把 FCM Token 保存到自己的服务端，再由受信任的服务端调用 Firebase Admin SDK 或 FCM HTTP v1 API 发消息。

Web FCM 的前置条件：

  • 站点必须运行在 HTTPS 下；本地开发使用浏览器认可的安全上下文
  • 需要一个根目录下的 firebase-messaging-sw.js
  • 需要在 Firebase 项目设置中生成 Web Push certificate（VAPID Key）
  • 浏览器必须支持 Push API，并且用户允许通知权限

初始化与获取 Token​

import { getMessaging, getToken, isSupported } from 'firebase/messaging'
import { app } from '@/lib/firebase/client'

export async function enablePush() {
  if (!(await isSupported())) return null

  const permission = await Notification.requestPermission()
  if (permission !== 'granted') return null

  const messaging = getMessaging(app)
  const registration = await navigator.serviceWorker.register(
    '/firebase-messaging-sw.js',
  )

  const token = await getToken(messaging, {
    vapidKey: import.meta.env.VITE_FIREBASE_VAPID_KEY,
    serviceWorkerRegistration: registration,
  })

  if (token) {
    await fetch('/api/push-tokens', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ token }),
    })
  }

  return token
}

VITE_FIREBASE_VAPID_KEY 是 Web Push 公钥，可以出现在前端；真正用于发送消息的服务账号凭证和 FCM 服务端调用权限不能放进浏览器。

Service Worker 与前台消息​

public/firebase-messaging-sw.js 至少要能被站点根路径访问。根据构建方式，可以在 Service Worker 中使用 compat SDK，或者通过构建产物提供模块化依赖；关键是最终浏览器请求 /firebase-messaging-sw.js 时不能得到 HTML fallback。

前台消息可以在页面中监听：

import { getMessaging, onMessage } from 'firebase/messaging'
import { app } from '@/lib/firebase/client'

export function watchForegroundMessage(
  onNotification: (payload: unknown) => void,
) {
  const messaging = getMessaging(app)
  return onMessage(messaging, onNotification)
}

可以按页面状态处理消息：

  • 页面处于前台：由页面展示 Toast、站内消息或未读数更新
  • 页面处于后台：由 Service Worker 展示系统通知，并在 notificationclick 中处理跳转

Token 生命周期和服务端存储​

FCM Token 不是用户永久身份，可能因为浏览器数据清理、权限变化、重新安装或 Service Worker 变化而更新。服务端表建议至少保存：

user_id
fcm_token
platform = web
user_agent / browser（可选）
last_seen_at
revoked_at（可选）

同一个用户可能有多个浏览器和设备，所以不要把 Token 设计成用户表上的单字段。发送失败时要删除已失效 Token；用户退出登录时，可以解绑当前浏览器 Token，但不要误删该用户其他设备的 Token。

Cloud Messaging 的常见坑​

  • 没有 HTTPS、通知权限被拒绝、浏览器不支持 Push API
  • Service Worker 文件不在站点根路径，或被 SPA fallback 返回成 index.html
  • VAPID Key 配错 Firebase 项目，导致 getToken() 失败
  • 只在前端拿 Token，却没有保存到服务端，后续无法按用户发送
  • 把 FCM Token 当成用户 ID 或长期稳定主键
  • 只测试前台消息，没有测试后台通知、点击跳转和浏览器关闭后的行为
  • 没有给通知跳转 URL 做白名单校验，导致点击通知产生开放重定向风险

官方 Web FCM 入门文档：Get started with Firebase Cloud Messaging in Web apps

Hosting​

适合托管静态站点和单页应用。官方现在也在推进更偏现代全栈场景的 App Hosting，但如果你的项目是传统前端站点，先理解 Hosting 就够了。

App Check​

它不是权限系统，而是“请求来源校验层”。适合用来减少接口、数据库、存储被脚本滥刷的风险。

集成前先定边界​

1. 先选要用的模块​

不必一次接入所有服务。常见组合有：

  • 只用 Auth：把登录体系先搭起来，数据库还是你自己的后端
  • Auth + Firestore + Storage：适合前端主导、迭代快的中小型产品
  • Auth + Functions：认证交给 Firebase，核心业务逻辑仍在你自己的服务端
  • 只把 Firebase 当周边能力：例如只用 FCM、Analytics、Remote Config

2. 确认项目有没有 SSR 或 API 层​

这会影响初始化方式和权限边界：

  • 纯前端 SPA：客户端直接接 Web SDK，重点看 Auth、Firestore、Storage、Rules
  • Next.js / Remix / Nuxt 这类带服务端渲染或 API 层的项目：客户端仍用 Web SDK，服务端再补 Admin SDK
  • 自己有 Node / Java / Go 后端：客户端只拿 Firebase 登录态，真正的业务写操作可以继续走自家 API

3. 决定是否让 Firebase 承担主数据库​

如果项目核心是：

  • 关系复杂
  • 统计报表重
  • 后台运营查询很多
  • 事务边界严格

这种情况下，Firebase 可以只负责认证、文件或消息推送，主数据继续放在关系型数据库中。

Web 项目接入​

Firebase 官方推荐使用 npm 模块化 Web SDK，并由打包器做 tree-shaking。React、Vue、Next 和 Vite 项目都可以按这个方式接入。官方 Web Setup

1. 安装 SDK​

pnpm add firebase

2. 准备环境变量​

Firebase Web 配置本身不是服务端密钥，可以放在前端环境变量里；真正敏感的是服务账号、第三方 secret、Admin SDK 凭证。

Vite 常见写法：

VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=...
VITE_FIREBASE_PROJECT_ID=...
VITE_FIREBASE_STORAGE_BUCKET=...
VITE_FIREBASE_MESSAGING_SENDER_ID=...
VITE_FIREBASE_APP_ID=...

Next.js 常见写法：

NEXT_PUBLIC_FIREBASE_API_KEY=...
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=...
NEXT_PUBLIC_FIREBASE_PROJECT_ID=...
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET=...
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=...
NEXT_PUBLIC_FIREBASE_APP_ID=...

3. 封装 Firebase Client​

// src/lib/firebase/client.ts
import { getApps, initializeApp } from 'firebase/app'
import { getAuth } from 'firebase/auth'
import { getFirestore } from 'firebase/firestore'
import { getStorage } from 'firebase/storage'

const firebaseConfig = {
  apiKey: import.meta.env.VITE_FIREBASE_API_KEY,
  authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
  projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
  storageBucket: import.meta.env.VITE_FIREBASE_STORAGE_BUCKET,
  messagingSenderId: import.meta.env.VITE_FIREBASE_MESSAGING_SENDER_ID,
  appId: import.meta.env.VITE_FIREBASE_APP_ID,
}

const app = getApps().length ? getApps()[0] : initializeApp(firebaseConfig)

export const auth = getAuth(app)
export const db = getFirestore(app)
export const storage = getStorage(app)

如果你是 Next.js，客户端初始化逻辑类似，只是环境变量名换成 NEXT_PUBLIC_*。

4. 登录态监听​

import { onAuthStateChanged } from 'firebase/auth'
import { auth } from './client'

export function watchAuthUser(callback: (uid: string | null) => void) {
  return onAuthStateChanged(auth, (user) => {
    callback(user?.uid ?? null)
  })
}

5. Firestore 读写​

import { addDoc, collection, getDocs, query, where } from 'firebase/firestore'
import { db } from './client'

export async function createPost(payload: { title: string; authorId: string }) {
  await addDoc(collection(db, 'posts'), {
    ...payload,
    createdAt: Date.now(),
  })
}

export async function listMyPosts(authorId: string) {
  const q = query(collection(db, 'posts'), where('authorId', '==', authorId))
  const snap = await getDocs(q)
  return snap.docs.map((doc) => ({
    id: doc.id,
    ...doc.data(),
  }))
}

6. Storage 上传​

import { getDownloadURL, ref, uploadBytes } from 'firebase/storage'
import { storage } from './client'

export async function uploadAvatar(file: File, uid: string) {
  const fileRef = ref(storage, `avatars/${uid}/${file.name}`)
  await uploadBytes(fileRef, file)
  return getDownloadURL(fileRef)
}

Google 和 Apple 登录​

Google 和 Apple 都通过 OAuth 登录，但配置和用户资料处理方式不同。

  • Google 登录配置相对简单，适合先用 popup 接入
  • Apple 登录更依赖 Apple Developer 配置，邮箱和用户姓名也有额外限制
  • 两者都能直接接到 Firebase Auth，再由 Firebase 统一给你产出用户对象和 ID Token
  • 业务系统还要处理账号合并、环境配置、移动端跳转和服务端校验

流程​

无论是 Google 还是 Apple，前端大体都是这条链路：

  1. 用户点击第三方登录按钮
  2. Firebase Auth 拉起对应 Provider 的 OAuth 流程
  3. Provider 登录成功后回到 Firebase
  4. Firebase 给前端返回 UserCredential
  5. 前端拿到 Firebase 用户信息和 ID Token
  6. 如果你有自家后端，再把 Firebase ID Token 发给服务端校验

如果项目还有自己的用户表，再加一步：

  1. 服务端根据 uid 或邮箱，把 Firebase 账号映射到你自己的业务用户

Google 登录​

Google 登录使用 GoogleAuthProvider，可以调用 signInWithPopup() 或 signInWithRedirect()。移动端通常更适合 redirect 流程。Google Sign-In for Web

控制台配置清单​

在 Firebase Console 的 Authentication -> Sign-in method 中启用 Google。基础 Provider 配置通常会自动生成，域名白名单需要自己检查。

环境Firebase Authorized domainsGoogle OAuth redirect URI
本地开发localhost（新项目可能要手动添加）通常由 Firebase 默认 authDomain 承接
测试环境staging.example.comhttps://<authDomain>/__/auth/handler
正式环境app.example.comhttps://<authDomain>/__/auth/handler

Authorized domains 只决定 Firebase Auth 是否接受从该站点发起的认证；如果你在 Google Cloud Console 自行维护 OAuth Client，还必须把 Firebase 回调地址加入该 Client 的 Authorized redirect URIs。默认的 authDomain 一般是 <project-id>.firebaseapp.com；如果希望登录页展示自己的域名，可以通过 Firebase Hosting 配置自定义认证域名，并在 Google OAuth Client 中使用 https://auth.example.com/__/auth/handler。官方对自定义域名和回调地址有专门说明。Google Sign-In for Web

Google 的 redirect URI 不填 http://localhost:5173 或页面的 /login。Firebase SDK 实际使用的是 authDomain 下的 /__/auth/handler。

最小接入代码​

import {
  GoogleAuthProvider,
  signInWithPopup,
  signInWithRedirect,
} from 'firebase/auth'
import { auth } from '@/lib/firebase/client'

const provider = new GoogleAuthProvider()

export async function signInWithGoogleByPopup() {
  const result = await signInWithPopup(auth, provider)
  return result.user
}

export function signInWithGoogleByRedirect() {
  return signInWithRedirect(auth, provider)
}

popup 和 redirect​

  • 桌面端后台、内容站、SaaS 控制台：先用 popup
  • 移动端 H5、内嵌浏览器或经常拦截弹窗的环境：用 redirect
  • 遇到第三方存储限制时，按 Firebase 的 redirect 最佳实践检查 authDomain 和代理配置

Firebase 官方在重定向最佳实践里提到，某些浏览器会拦第三方存储访问；一种直接的处理方式就是改用 signInWithPopup()，另一类方案是调整 authDomain 或做反向代理。Redirect Best Practices

Scope 和自定义参数​

  1. 额外 scope

如果还要调用 Google API，可以为 Provider 添加 scope。只做登录时不要申请无关权限。Google Sign-In for Web

const provider = new GoogleAuthProvider()
provider.addScope('https://www.googleapis.com/auth/contacts.readonly')
  1. 自定义参数

例如登录页预填邮箱：

const provider = new GoogleAuthProvider()

provider.setCustomParameters({
  login_hint: 'user@example.com',
})

也可以在 auth 实例上设置 languageCode，让登录流程使用指定语言。Google Sign-In for Web

auth.languageCode = 'zh-CN'

登录成功后能拿到什么​

Google 登录完成后，除了 Firebase 用户对象，还可以从结果里取到 Google OAuth Access Token。官方示例里通过 GoogleAuthProvider.credentialFromResult(result) 读取 accessToken。Google Sign-In for Web

import {
  GoogleAuthProvider,
  signInWithPopup,
} from 'firebase/auth'

const provider = new GoogleAuthProvider()
const result = await signInWithPopup(auth, provider)

const credential = GoogleAuthProvider.credentialFromResult(result)
const googleAccessToken = credential?.accessToken
const firebaseUser = result.user

这里有两种 token：

  • Google OAuth Access Token：给 Google API 用
  • Firebase ID Token：给你自己的后端校验登录态用

用途不同，不要混用。

如果你有自家后端，推荐怎么接​

Google Access Token 不应作为业务系统的登录凭证。流程可以这样做：

  1. 前端用 Firebase 完成 Google 登录
  2. 前端调用 currentUser.getIdToken()
  3. 把 Firebase ID Token 发给你自己的后端
  4. 服务端用 Firebase Admin SDK 校验这个 ID Token
  5. 校验通过后，再建立你自己的 session 或业务登录态

前端示例：

export async function loginWithGoogleAndExchangeSession() {
  const provider = new GoogleAuthProvider()
  const result = await signInWithPopup(auth, provider)
  const idToken = await result.user.getIdToken()

  await fetch('/api/auth/firebase/session', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ idToken }),
  })
}

Google 登录排查​

  • 只做了 Firebase Console 配置，没把正式域名加入 authorized domains
  • 2025 年 4 月 28 日以后创建的 Firebase 项目，localhost 不再默认位于 Authorized domains；本地调试失败时先检查这里。Email Link Auth 文档
  • 本地、测试、正式环境共用同一个 OAuth 配置，最后回调域名全乱了
  • 把 Google Access Token 错当成自家业务登录凭证
  • 重定向流程没处理浏览器第三方存储限制
  • 用户已用别的 Provider 注册过相同邮箱，但你没处理账号合并

Apple 登录​

Firebase 官方 Web 文档里，Apple 登录使用 OAuthProvider('apple.com')，同样支持 popup 和 redirect；官方也明确写了，移动端更偏向 redirect。Apple Sign-In for Web

Apple Developer 和 Firebase Console 配置清单​

Apple 登录的难点在 Apple Developer 和 Firebase 两边的配置。按下面的顺序操作：

  1. 在 Apple Developer 账号中创建 Services ID，它是 Web 登录时使用的 Client ID。
  2. 为该 Services ID 开启 Sign in with Apple，填写你的站点域名和回调地址：https://<authDomain>/__/auth/handler。
  3. 创建一个用于 Sign in with Apple 的 Key，记录 Key ID，并下载一次性的 .p8 私钥文件；私钥不要提交到仓库。
  4. 记录 Apple Team ID、Services ID（Client ID）、Key ID 和 .p8 私钥内容。
  5. 回到 Firebase Console 的 Authentication -> Sign-in method -> Apple，填入上述参数并启用 Provider。
  6. 把实际站点域名加入 Firebase 的 Authorized domains。

Apple Developer 中的域名和 Return URL 必须配置。使用自定义 authDomain 时，Apple 端也要填写相应的 <authDomain>/__/auth/handler。Firebase 的 Apple Provider 还需要 Services ID、Team ID、Key ID 和私钥。Apple Sign-In for Web

建议把 Apple Key 的 .p8 原文只放进 CI/CD 或 Firebase Console 的受控配置中。它是私钥，和前端 Firebase apiKey 完全不是同一类东西。

最小接入代码​

import {
  OAuthProvider,
  signInWithPopup,
  signInWithRedirect,
} from 'firebase/auth'
import { auth } from '@/lib/firebase/client'

const provider = new OAuthProvider('apple.com')

export async function signInWithAppleByPopup() {
  const result = await signInWithPopup(auth, provider)
  return result.user
}

export function signInWithAppleByRedirect() {
  return signInWithRedirect(auth, provider)
}

Apple 与 Google 的差异​

  1. Apple 对用户信息更克制

Firebase 官方文档明确提到，Apple 不提供头像 URL；而且用户显示名这类信息通常只会在第一次登录时提供一次。Apple Sign-In for Web

因此：

  • 不要依赖后续登录重新返回昵称
  • 首次登录拿到名字后立即落库
  • 头像需要由你的资料页补充
  1. 用户可能隐藏真实邮箱

官方文档说明，用户可以选择隐藏邮箱，这时 Apple 会给出 privaterelay.appleid.com 域名的匿名邮箱地址。Apple Sign-In for Web

这会影响业务建模：

  • 邮箱不一定是真实邮箱
  • 发邮件、识别账号和客服排查都要支持 relay 邮箱
  1. Apple 账号链接有额外合规要求

Firebase 官方写得很直接：把 Apple 账号和其他身份数据做链接前，你需要先获得用户明确同意。Apple Sign-In for Web

游客账号绑定 Apple 时尤其要处理这一步。

Scope 和语言​

  1. 请求 email 和 name
const provider = new OAuthProvider('apple.com')
provider.addScope('email')
provider.addScope('name')

当 Firebase 启用“一邮箱一账号”策略时，默认会请求 email 和 name；改成“一个邮箱可对应多个账号”后，需要显式添加 scope。Apple Sign-In for Web

  1. 设置语言
const provider = new OAuthProvider('apple.com')

provider.setCustomParameters({
  locale: 'zh_CN',
})

登录成功后能拿到什么​

Apple 登录完成后，可以从 OAuthProvider.credentialFromResult(result) 里拿到 accessToken 和 idToken。Apple Sign-In for Web

import { OAuthProvider, signInWithPopup } from 'firebase/auth'

const provider = new OAuthProvider('apple.com')
const result = await signInWithPopup(auth, provider)

const credential = OAuthProvider.credentialFromResult(result)
const appleAccessToken = credential?.accessToken
const appleIdToken = credential?.idToken
const firebaseUser = result.user

业务系统通常只需要 Firebase 用户对象和 Firebase ID Token。Apple 原始 token 只在需要调用 Apple 相关能力时使用。

Apple 登录排查​

  1. 把 Apple 当成 Google 的另一个实现。Apple 对邮箱、姓名、匿名化和账号链接有自己的限制。

  2. 没有保存首次登录时的信息

Apple 的名字信息通常只给一次。首次登录不保存，后续很难补回。

  1. 忽略 relay 邮箱

如果你的业务把邮箱当成“天然唯一且可直联络”的主键，Apple 登录会把这个假设打破。

  1. 忽略移动端和 Safari 行为

Apple 登录在移动端和 Safari 环境里更需要认真测 redirect 流程、回跳域名、cookie/session 保持和授权后的页面恢复。

  1. 忘记配置 Apple 邮件转发

如果项目使用 Firebase Auth 发送验证邮件、邮件链接登录、密码重置或账号变更通知，必须在 Apple Developer 的 private email relay 配置中登记 Firebase 发信地址，例如 noreply@<project-id>.firebaseapp.com，或你自定义邮件模板使用的发信域名。否则邮件不会被转发给选择隐藏邮箱的 Apple 用户。Apple Sign-In for Web

redirect 登录的回跳处理​

signInWithRedirect() 发起后，当前页面会离开；登录成功重新回到应用时，结果不会从原函数直接返回。应用启动时要调用 getRedirectResult() 读取结果，并统一做后续的用户落库、交换业务 Session 和页面恢复。

import { getRedirectResult } from 'firebase/auth'
import { auth } from '@/lib/firebase/client'

export async function finishRedirectSignIn() {
  const result = await getRedirectResult(auth)
  if (!result) return null

  const idToken = await result.user.getIdToken()
  await exchangeFirebaseSession(idToken)
  return result.user
}

在 React / Vue 的应用根节点调用一次即可。跳转前把原目标页存进 sessionStorage，登录完成后再恢复。不要把 OAuth 返回数据或 token 写进 URL。

const returnTo = `${location.pathname}${location.search}`
sessionStorage.setItem('auth:return-to', returnTo)

// 登录成功后
const target = sessionStorage.getItem('auth:return-to') || '/'
sessionStorage.removeItem('auth:return-to')
location.assign(target)

同邮箱但不同 Provider 的冲突处理​

当 Firebase 开启“一邮箱一账号”策略时，用户可能先以邮箱密码注册，又点了 Google 登录。此时 Firebase 会返回 auth/account-exists-with-different-credential；Google 登录文档也明确说明该错误会携带待链接的 credential。Google Sign-In for Web

不要让前端静默创建第二个业务用户。先让用户用已有方式登录，确认身份后，再把新的 Provider 链接到当前用户。

import {
  GoogleAuthProvider,
  linkWithCredential,
  signInWithPopup,
} from 'firebase/auth'

export async function tryGoogleSignIn() {
  try {
    return await signInWithPopup(auth, new GoogleAuthProvider())
  } catch (error: unknown) {
    const code = (error as { code?: string }).code
    if (code !== 'auth/account-exists-with-different-credential') throw error

    const pending = GoogleAuthProvider.credentialFromError(error)
    // 此处转到“使用原登录方式登录”的交互；成功后再执行：
    if (auth.currentUser && pending) {
      return linkWithCredential(auth.currentUser, pending)
    }
    throw error
  }
}

上例省略了交互部分。实际页面要先完成原 Provider 的重新认证，再执行 linkWithCredential()。绑定 Apple 前，应明确告知用户绑定的结果并取得同意。

账号合并​

需要考虑这些情况：

  • 用户先用邮箱密码注册
  • 后来又点了 Google 登录
  • 或者先用了 Apple 隐藏邮箱登录，后来又想绑定 Google

Firebase 官方提供了链接多个 Provider 的能力，Web 端可以用 linkWithPopup() 或对应的 redirect 流程来做账号绑定。Link Multiple Providers

例如把 Google 绑定到当前已登录用户：

import { GoogleAuthProvider, linkWithPopup } from 'firebase/auth'
import { auth } from '@/lib/firebase/client'

export async function linkGoogleProvider() {
  const user = auth.currentUser
  if (!user) throw new Error('No active user')

  const provider = new GoogleAuthProvider()
  await linkWithPopup(user, provider)
}

产品层先定下这条身份规则：

  • 以 Firebase uid 为主身份
  • 邮箱只是辅助识别字段
  • 第三方 Provider 是登录入口，不是唯一用户主键

这样 Apple 隐藏邮箱、Google 邮箱和邮箱密码登录可以共存。

Web 项目的落地选择​

常规 Web 应用可以按下面的方式落地：

  1. 桌面端优先用 popup
  2. 移动端或 Safari 敏感场景准备 redirect
  3. 统一封装 signInWithGoogle()、signInWithApple()，不要把 Provider 细节散在页面里
  4. 首次登录后，立刻把用户基础资料写入你的用户表
  5. 所有后端鉴权一律校验 Firebase ID Token，不直接信任前端传来的 Provider token
  6. 提前设计账号绑定和冲突处理，不要等线上出现同邮箱多账号再补

认证模块示例​

import {
  GoogleAuthProvider,
  OAuthProvider,
  signInWithPopup,
  signInWithRedirect,
  UserCredential,
} from 'firebase/auth'
import { auth } from '@/lib/firebase/client'

function isMobileLike() {
  return /iPhone|iPad|iPod|Android/i.test(window.navigator.userAgent)
}

async function resolveAuthFlow(provider: GoogleAuthProvider | OAuthProvider) {
  if (isMobileLike()) {
    await signInWithRedirect(auth, provider)
    return null
  }

  return signInWithPopup(auth, provider)
}

export async function signInWithGoogle(): Promise<UserCredential | null> {
  const provider = new GoogleAuthProvider()
  provider.setCustomParameters({ login_hint: 'user@example.com' })
  return resolveAuthFlow(provider)
}

export async function signInWithApple(): Promise<UserCredential | null> {
  const provider = new OAuthProvider('apple.com')
  provider.addScope('email')
  provider.addScope('name')
  provider.setCustomParameters({ locale: 'zh_CN' })
  return resolveAuthFlow(provider)
}

把 Provider 细节放进认证模块后：

  • 页面层只关心“用户点了哪个登录按钮”
  • 设备差异和 Provider 差异都收口在认证模块
  • 埋点、异常上报和账号绑定逻辑都有固定入口

服务端集成时，客户端 SDK 和 Admin SDK 要分清​

客户端 SDK 和 Admin SDK 的边界要单独处理。

客户端 SDK 负责什么​

  • 登录
  • 拿当前用户 Token
  • 直接访问 Firestore / Storage / Messaging 等前端能力

Admin SDK 负责什么​

  • 校验用户 ID Token
  • 管理用户
  • 绕过 Security Rules 执行受信任操作
  • 发送推送
  • 执行批量管理任务

Firebase 官方的 Admin SDK 文档里明确区分了服务端初始化方式，Node 侧通常是 initializeApp()，并通过环境变量或默认凭证读取配置。官方 Admin Setup

Node 服务端示例：

// server/firebase-admin.ts
import { applicationDefault, getApps, initializeApp } from 'firebase-admin/app'
import { getAuth } from 'firebase-admin/auth'

const app =
  getApps().length > 0
    ? getApps()[0]
    : initializeApp({
        credential: applicationDefault(),
      })

export const adminAuth = getAuth(app)

校验前端带来的 ID Token：

export async function verifyUser(idToken: string) {
  const decoded = await adminAuth.verifyIdToken(idToken)
  return decoded.uid
}

有 SSR 或自家 API 时，用 HttpOnly Cookie 建立业务 Session​

有 SSR、BFF 或自家 API 时，可以在首次登录后把 Firebase ID Token 换成 HttpOnly Session Cookie。浏览器脚本无法读取 Cookie，SSR 和服务端接口可以直接校验它。纯 API 项目则可以继续使用 Authorization 请求头传递 ID Token。

流程是：

  1. 前端完成 Google / Apple 登录，拿到 Firebase ID Token。
  2. 前端 POST /api/auth/session，携带 ID Token 和 CSRF 防护信息。
  3. 服务端验证 ID Token，确认是刚刚完成登录的用户。
  4. 服务端调用 Admin SDK 的 createSessionCookie()，以 HttpOnly、Secure Cookie 返回。
  5. 后续 SSR 和 API 使用 verifySessionCookie() 识别用户。

Firebase 官方支持 5 分钟到 2 周有效期的 Session Cookie，并建议在创建 Cookie 前检查 auth_time，避免被窃取的旧 ID Token 换取新会话。Manage Session Cookies

以 Node / Express 风格为例：

import { adminAuth } from './firebase-admin'

const SESSION_MAX_AGE = 1000 * 60 * 60 * 24 * 5

app.post('/api/auth/session', async (req, res) => {
  const { idToken } = req.body as { idToken?: string }
  if (!idToken) return res.status(400).json({ message: 'Missing idToken' })

  const decoded = await adminAuth.verifyIdToken(idToken)
  const signedInRecently = Date.now() / 1000 - decoded.auth_time < 5 * 60
  if (!signedInRecently) {
    return res.status(401).json({ message: 'Recent sign-in required' })
  }

  const session = await adminAuth.createSessionCookie(idToken, {
    expiresIn: SESSION_MAX_AGE,
  })

  res.cookie('__Host-session', session, {
    httpOnly: true,
    secure: true,
    sameSite: 'lax',
    path: '/',
    maxAge: SESSION_MAX_AGE,
  })
  return res.status(204).end()
})

__Host- 前缀要求 Cookie 使用 Secure、路径为 /，且不设置 Domain，适合前端和 API 共用一个主域名的应用。前端与 API 分属不同站点时，还要一起处理 SameSite、CORS 和 CSRF，不要为了跨站请求直接设为 SameSite=None。

校验受保护请求：

app.get('/api/me', async (req, res) => {
  const session = req.cookies['__Host-session']
  if (!session) return res.status(401).end()

  try {
    const user = await adminAuth.verifySessionCookie(session, true)
    return res.json({ uid: user.uid, email: user.email ?? null })
  } catch {
    res.clearCookie('__Host-session', { path: '/' })
    return res.status(401).end()
  }
})

退出登录至少要清除 Cookie；若是“退出所有设备”或怀疑会话泄露，再调用 revokeRefreshTokens(uid)，使该用户的现有 Session Cookie 和刷新令牌失效。Firebase 也提醒：带 checkRevoked: true 的校验会额外产生一次网络请求，因此可按接口敏感程度决定使用位置。Manage Session Cookies

app.post('/api/auth/logout', async (req, res) => {
  res.clearCookie('__Host-session', { path: '/' })
  return res.status(204).end()
})

前端完成 Cookie 交换后，可以调用 signOut(auth) 清除 SDK 的本地状态，避免客户端持久化和服务端 Session 出现两套长期登录态；后续以服务端 Cookie 为准。

一个可以直接拆进项目的目录结构​

src/
  lib/firebase/client.ts       # Web SDK 初始化
  lib/auth/providers.ts        # Google / Apple Provider 与 popup/redirect 选择
  lib/auth/redirect.ts         # getRedirectResult 与 returnTo 恢复
  lib/auth/session.ts          # ID Token 交换业务 Session
server/
  firebase-admin.ts            # Admin SDK 初始化，只能在服务端导入
  routes/auth-session.ts       # Session 创建、校验、退出

边界很简单：client.ts 可以被浏览器代码引用，firebase-admin.ts 绝不能进入前端 bundle；页面组件只调用 providers.ts 暴露的业务函数，不自己创建 Provider。

Auth、Rules、App Check 的分工​

这三层处理不同问题：

  • Auth：你是谁
  • Security Rules：你能读写什么
  • App Check：这个请求是不是来自你信任的应用环境

一个常见误区​

前端拿到登录用户后，仍然不能读写任意文档。权限要由 Firestore Rules、Storage Rules 或服务端接口执行。

例如只允许用户读写自己的文档：

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
  }
}

Security Rules 在服务端强制执行，可以为文档和对象路径设置细粒度权限。官方 Security Rules

App Check 什么时候要上​

如果你的项目已经开始面临这些问题，就该考虑上 App Check：

  • 公网前端接口被脚本刷
  • Storage 下载或上传成本异常
  • Firestore 请求量明显异常
  • 你希望把“登录用户”和“可信应用来源”分开校验

Web 端集成 App Check 时，官方文档给的是在访问其他 Firebase 服务前初始化 initializeAppCheck(...) 的方式。官方 App Check Web

本地开发和环境隔离​

Firebase 官方提供了 Local Emulator Suite，可以在本地模拟 Firestore、Auth、Storage、Functions、Hosting 等能力，用来做集成测试、手动联调和 CI 验证，而且不碰生产数据。官方 Emulator Suite

基本流程：

pnpm add -D firebase-tools
pnpm exec firebase login
pnpm exec firebase init
pnpm exec firebase emulators:start

环境安排可以是：

  • 开发环境先连 emulator
  • 测试环境单独用一个 Firebase project
  • 正式环境独立 project，不和测试共用
  • 不要拿生产 project 兼任日常开发

工程约定​

1. 客户端只放公开配置，不放服务端密钥​

apiKey、authDomain、projectId 这类 Web 配置不是秘密；服务账号 JSON、第三方接口密钥、支付签名密钥才是秘密。

2. 只把“适合前端直连”的能力交给客户端​

例如：

  • 用户自己的草稿、个人资料、轻交互数据：可以考虑前端直连 Firestore
  • 支付、结算、风控、聚合写入、跨用户敏感操作：尽量走服务端

3. 规则设计先于页面开发​

不要等页面都写完了才补 Rules。否则前期为了方便全开权限，后面很容易收不回来。

4. 尽早做环境隔离​

至少拆成：

  • dev
  • staging
  • prod

每套环境对应自己的 Firebase Project、配置和部署入口。

5. 关注监控和配额​

Firebase 接起来很快，账单涨起来也可能很快。尤其是这些地方要重点盯：

  • Firestore 读次数
  • Storage 出网流量
  • Cloud Functions 调用次数和执行时长
  • FCM、Analytics、Crashlytics 是否真的都需要接

常见问题​

1. 把 Firebase 当成“没有后端的后端”​

Firebase 可以减少后端搭建工作，但权限模型、数据模型、审计和成本控制仍然要自己设计。

2. 客户端和服务端都在乱写初始化​

一个项目里通常至少要明确两套入口：

  • firebase client
  • firebase admin

混在一个文件里，后面很容易把服务端依赖打进浏览器包。

3. 规则过宽​

最危险的不是 SDK 代码写错，而是测试阶段为了省事把规则开太大，最后忘记收。

4. Firestore 建模完全照搬 SQL 思路​

文档数据库不是不能建关系，而是你要重新想清楚：

  • 文档粒度
  • 聚合字段
  • 查询路径
  • 实时监听范围

5. 还没分环境就开始接正式项目​

这会让测试数据污染正式环境，也会让规则调试和计费分析变得很乱。

适合使用 Firebase 的场景​

  • 你想让前端团队快速交付第一版
  • 项目需要 Auth、实时数据、对象存储、推送这类现成能力
  • 业务关系没有重到必须用复杂 SQL
  • 你接受围绕 Google Cloud / Firebase 生态来组织工程

什么时候要谨慎一些​

  • 核心业务事务复杂
  • 强依赖复杂报表和多表分析
  • 成本预估必须非常可控
  • 权限模型非常重，且团队还不熟悉 Security Rules
  • 你更希望核心数据层留在通用数据库和自建后端里

一个比较稳的落地顺序​

如果项目决定使用 Firebase，可以按下面的顺序推进：

  1. 先定范围：只接 Auth，还是把 Firestore / Storage 也一起接入
  2. 建三个环境：dev、staging、prod
  3. 先封装 client 和 admin 两套初始化入口
  4. 先写最小可用 Rules，再开始页面开发
  5. 本地先打通 Emulator Suite
  6. 最后再补 App Check、监控、计费告警和部署流程
